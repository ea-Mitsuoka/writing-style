# 要件定義 — writing-style

このリポジトリ（日本語表現ルールの改善ループの仕組み）が満たす要件を、所有者と AI エージェント
のために定める。現時点の対象は最初の取り組み「表現ルールの検証」（issue #3）。

## 1. 用語

用語の定義は [docs/glossary.md](glossary.md) に一度だけ置き、本書は名前で参照する。

## 2. 前提と制約

| ID | 種別 | 内容 | 外れた場合の影響 |
| -- | -- | -- | -- |
| A-1 | 前提 | 表現ルールの本文は Vault の `30_memory/feedback/ja-<kind>-<slug>.md` にあり、書式は Vault の `AGENTS.md`「表現ルール」節が定める | 検査項目の根拠が失われる。Vault 側の書式変更に本書と実装を追随させる |
| A-2 | 前提 | 利用者はこのリポジトリと Vault を同じ機械に置き、`OBSIDIAN_VAULT_PATH` を設定している | ローカル検証で Vault の場所を毎回指定する必要がある |
| C-1 | 制約 | Vault は Private で、このリポジトリの CI からは読めない | CI での検証は同梱 fixture に限る（ADR-0001） |
| C-2 | 制約 | 実装は標準ライブラリのみ（`.ai/architecture.md`） | 依存追加には GR-023 の理由付けが要る |
| C-3 | 制約 | 検証は Vault に書き込まない | 自動修正機能は対象外 |

## 3. 目的と範囲

- **目的（一文）:** 表現ルールの書式違反、特に適用範囲の欠落を、Vault に保存される前に
  機械的に検出する。

- **成功指標（測定可能）:**

  | 指標 | 目標 | 測定方法 |
  | -- | -- | -- |
  | 書式違反の検出 | §4 の各要件に対応する違反 fixture を 100 % 検出する | 単体テスト（違反 fixture ごとに 1 件） |
  | 誤検知 | 書式に適合する fixture に対する検証結果が 0 件 | 単体テスト（Vault の試作ルールを写した fixture） |
  | 実行時間 | ルール 100 件で 1 秒以内 | ローカル計測（NFR-001） |

- **範囲:** `ja-*` ルールファイルの構造検証と、その CLI。

- **対象外（明示）:** 案件名・顧客名の混入検出。安定判定と Skill への昇格。Vault への
  書き込みや自動修正。Claude Code セッション記録からの指摘抽出（別の取り組み）。

- **関係者:**

  | 役割 | 関心 | 決定権限 |
  | -- | -- | -- |
  | リポジトリ所有者 | ルールが誤適用されないこと。運用の手間が増えないこと | 要件・優先度・受け入れ |
  | AI エージェント | 検証結果を読んでルールを修正できること | なし（提案のみ） |

## 4. 機能要件

| ID | 要件 | 目的との対応 | 優先度 | 根拠 |
| -- | -- | -- | -- | -- |
| FR-001 | 対象ファイルは Vault の `30_memory/feedback/` 直下の `ja-*.md` に限る。他のファイルは検証しない | 誤検知 0 | Must | 他の `feedback` メモリは共通書式のみが対象で、Vault 側 CI が検査する |
| FR-002 | ファイル名（拡張子なし）が `ja-(term\|style\|structure)-[a-z0-9-]+` に一致し、frontmatter `name` と等しいこと | 検出 100 % | Must | `AGENTS.md` の命名規則。Vault 側も `name` = ファイル名を要求 |
| FR-003 | ファイル名の `<kind>` と `metadata.kind` が等しく、値が `term` / `style` / `structure` のいずれかであること | 検出 100 % | Must | `AGENTS.md` の `kind` 定義 |
| FR-004 | `metadata.type` が `feedback` であること | 検出 100 % | Must | 表現ルールは `feedback` 型の派生 |
| FR-005 | `metadata.scope` が `[a, b]` 形式で、定義済みタグ（customer-doc / decision-doc / internal-doc / slide / chat / code）の 1 つ以上からなり、重複がないこと | 検出 100 % | Must | 適用範囲の欠落が最も重い事故につながる |
| FR-006 | `updated` が実在する日付の `YYYY-MM-DD` であること | 検出 100 % | Must | 安定判定（将来）の入力になる |
| FR-007 | `description` が空でないこと | 検出 100 % | Must | 索引と想起判定に使う |
| FR-008 | 本文に見出し `## ルール` と `## NG / OK` がこの順で 1 回ずつあること | 検出 100 % | Must | `AGENTS.md` の本文順序 |
| FR-009 | `## NG / OK` 節の表に、NG 列と OK 列の両方が空でない行が 1 行以上あること（見出し行・区切り行を除く） | 検出 100 % | Must | 具体例の対が再発防止の要 |
| FR-010 | 本文に `**Why:**` と `**How to apply:**` があること | 検出 100 % | Must | `feedback` 共通書式 |
| FR-011 | CLI は `--vault <path>` を受け取り、省略時は `OBSIDIAN_VAULT_PATH` を使う。どちらも無ければ理由を示して終了コード 2 | 運用の手間 | Must | A-2 |
| FR-012 | 検証結果は 1 件 1 行で `相対パス:コード:メッセージ` の形式で標準出力に出し、結果が 1 件以上なら終了コード 1、0 件なら 0 | AI が読んで修正できる | Must | CI・フックからの利用 |
| FR-013 | frontmatter が解析できないファイルは、他の項目を検査せず「解析不能」を 1 件だけ報告する | 誤検知 0 | Should | 二次的な結果の連鎖を避ける |

### 4.1 利用シナリオ

1. 所有者または AI がルールを Vault に書く → `make rules-validate` を実行 → 結果 0 件なら
   Vault にコミットする。
2. 結果がある場合、`パス:コード:メッセージ` を読んでファイルを直し、再実行する。

### 4.2 業務ルール

- 検査項目の根拠はすべて Vault の `AGENTS.md`「表現ルール」節。本書と実装は同節に追随する。
- `scope` タグの語彙はコード内の定数 1 か所に置き、`AGENTS.md` を出典として注記する。

### 4.3 状態と遷移

対象外（状態を持たない）。

### 4.4 役割と権限

対象外（ローカル実行のみ。Vault の読み取り権限は OS のファイル権限に従う）。

### 4.5 エラーと例外

| 状況 | 振る舞い |
| -- | -- |
| Vault のパスが存在しない、または `30_memory/feedback/` が無い | 理由を標準エラーに出し、終了コード 2 |
| ファイルが UTF-8 として読めない | FR-013 と同様に「解析不能」1 件 |
| 対象ファイルが 0 件 | 結果 0 件、終了コード 0、対象 0 件である旨を標準出力に出す |

## 5. 非機能要件

| ID | 特性（ISO/IEC 25010） | 要件 | 目標 | 測定方法 | 優先度 |
| -- | -- | -- | -- | -- | -- |
| NFR-001 | 性能効率性 | ルール 100 件の検証 | 1 秒以内 | ローカルで `time make rules-validate` | Should |
| NFR-002 | 信頼性 | 決定的であること | 同じ入力に同じ出力 | 単体テストが乱数・時刻・ネットワークに依存しない（TST-010） | Must |
| NFR-003 | セキュリティ | Vault に書き込まない。ファイル内容をログや例外に丸ごと出さない | 書き込み API を持たない | コードレビュー、`infrastructure` の API 表面 | Must |
| NFR-004 | 保守性 | 4 層構成と依存方向（ARC-001/002）。`domain` / `application` の行カバレッジ | 80 % 以上 | `make coverage` | Must |
| NFR-007 | 移植性 | 標準ライブラリのみ、Python 3.11 以上 | 追加依存 0 | `pyproject.toml` の `dependencies = []` | Must |

## 6. データ要件

| 観点 | 仕様 |
| -- | -- |
| データモデル | 入力: Markdown ファイル（frontmatter + 本文）。出力: 検証結果（相対パス・コード・メッセージ）の列 |
| 想定量 | 数十〜数百ファイル |
| 保持 | 保持しない（読み取りのみ） |
| PII | ルール本文に個人名・顧客名を書かない運用（Vault `AGENTS.md`）。本モジュールは内容を保存・送信しない |
| バックアップ | 対象外（Vault が Git で管理） |

対象外。ローカル CLI と GitHub Actions（既存の CI 枠内）で完結し、追加のインフラ・課金は
発生しない。

| 監視 | 対象外 |

## 10. 受け入れ基準

| ID | 基準 | 検証する要件 | 検証方法 |
| -- | -- | -- | -- |
| AC-1 | FR-002〜FR-010 のそれぞれについて、違反 fixture が該当コードで検出され、適合 fixture では検出されない | FR-002〜010 | 単体テスト（要件ごとに違反・適合の対） |
| AC-2 | Vault の試作ルール `ja-term-gc-iam-roles.md` を写した fixture で結果が 0 件 | FR-001〜010 | 単体テスト |
| AC-3 | `--vault` 省略・`OBSIDIAN_VAULT_PATH` 未設定で終了コード 2、結果ありで 1、なしで 0 | FR-011, FR-012 | 単体テスト（CLI を関数として呼ぶ） |
| AC-4 | `make rules-validate` が実 Vault に対して動く | FR-011, A-2 | 所有者のローカル実行（PR に結果を記載） |
| AC-5 | `domain` / `application` の行カバレッジ 80 % 以上 | NFR-004 | `make coverage` |
