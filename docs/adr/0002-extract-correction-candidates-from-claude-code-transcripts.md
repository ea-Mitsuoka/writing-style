# ADR-0002: 指摘候補の抽出を、記録を読むだけの独立モジュールと人の仕分けで行う

## Context

改善ループの「抽出」段階では、利用者が過去のセッションで AI の日本語表現に対して行った指摘を
集める必要がある。利用者が常用するのは Claude Code で、その記録は
`~/.claude/projects/<プロジェクト>/<セッション>.jsonl` にローカル保存されている（2026-09-18 時点で
60 ファイル、502 MB、人間の発話 4,556 ターン）。

制約と観測は次のとおり。

- 標準ライブラリだけでは「指摘か否か」を意味で判定できない。語句一致は再現率を確保できるが
  精度が低い（「ではなく」「直して」の大半は通常の作業指示）。
- 抜粋には人名・案件名・顧客名が含まれる。リポジトリにも Vault にも入れられない。
- 既存の `rules` モジュールは「Vault のルールを検証する」責務で、記録の読み取りとは変更理由が
  異なる（MNT-001: 1 コンポーネント 1 つの変更理由）。
- 記録の形式は Anthropic の公開仕様ではなく、変わり得る。

## Options considered

### Option 1: 何もしない（利用者が記憶と検索で回収する）

元方針が指摘したとおり、キーワード検索は網羅できず、記憶は漏れる。実装コストはないが、
ループの起点が人力で止まる。

### Option 2: `rules` モジュールに抽出を足す

コード量は最小だが、`rules` に「記録の読み取り・スコア付け」という別の変更理由が入り、
記録形式の変更が検証モジュールのリリースに波及する。MNT-002 の分解判断に反する。

### Option 3: 抽出専用モジュール + 語句の重み付け + 人と AI の仕分け（採用）

`src/modules/extraction/` を独立した境界コンテキストとし、記録の読み取り（infrastructure）、
発話の選別とスコア付け（domain）、候補一覧の生成（application）、CLI（interface）に分ける。
スクリプトは**候補**を出すだけで、ルール化の判断は Claude Code セッションでの AI の提案と
利用者の確定に委ねる。出力は `out/` に限る。

### Option 4: 外部の形態素解析・機械学習ライブラリで指摘を分類する

精度は上がり得るが、依存が増え（GR-023）、学習データも無い。仕分け工程で AI を使えば同等の
効果が依存なしで得られる。

## Decision

Option 3 を採用する。

- 抽出は `src/modules/extraction/` に置く。`rules` とは独立し、互いの内部を import しない。
- スクリプトの責務は「候補一覧の生成」まで。指摘か否かの最終判定とルール化は、人と AI が行う。役割分担は
  `docs/requirements/extraction.md` §4.1、操作手順は `docs/runbook/triage-correction-candidates.md`。
- 記録には書き込まない。出力は `--out`（既定 `out/`、gitignore 済み）の 1 ファイルのみ。
  標準出力に抜粋を出さない。
- スコアは語句の重み付け（`#表現` 最優先、強・弱キーワード）で、値と条件は要件定義に書き、
  テストの期待値はそこから取る。
- 記録形式への依存は infrastructure に閉じ、domain は「発話」と「直前の assistant 本文」という
  形式非依存のモデルだけを扱う。

## Consequences

**Positive:** 見落としの少ない候補一覧が機械的に得られ、仕分けの負担はスコア順で下がる。
記録形式の変更は読み取り部だけに波及する。依存は増えない。機密は `out/` に閉じる。

**Negative:** 精度は語句次第で、キーワードを使わない指摘は拾えない（`#表現` タグ運用で今後を
補う）。仕分けは人の作業として残る。`out/` の運用規律（commit しない・共有しない）に依存する。

**Follow-ups:**

- 仕分けで見落としが出たときのキーワード見直し手順（要件 Q-101）。
- claude.ai エクスポートの解析（要件 Q-102、優先度低）。
