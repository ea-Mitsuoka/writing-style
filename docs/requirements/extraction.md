# 要件定義 — 指摘候補の抽出（Claude Code セッション記録）

改善ループの「抽出」段階を担う取り組み（issue #8）の要件。プロジェクト全体の要件と用語は
[docs/requirements.md](../requirements.md) と [docs/glossary.md](../glossary.md) が持ち、本書は
この取り組みに固有の事項だけを定める。

## 1. 用語

[docs/glossary.md](../glossary.md) の「セッション記録」「候補」「仕分け」「強キーワード / 弱キーワード」を
使う。

## 2. 前提と制約

| ID | 種別 | 内容 | 外れた場合の影響 |
| -- | -- | -- | -- |
| A-1 | 前提 | セッション記録は `~/.claude/projects/<プロジェクト>/<セッション ID>.jsonl`。1 行 1 レコードの JSON で、`type` が `user` / `assistant` のレコードが対話を表す（2026-09-18 に 60 ファイルで確認） | 形式が変われば読み取り部（infrastructure）だけを直す。判定と出力は影響を受けない |
| A-2 | 前提 | 利用者の指摘は、AI の出力の直後の人間の発話として現れる | 対にする assistant 本文が誤る。仕分け時に人が気づける |
| A-3 | 前提 | 標準ライブラリだけでは指摘か否かを意味で判定できない。語句の重み付けで**候補**を出し、判定は人と AI の仕分けに委ねる | 精度を上げるには仕分け工程が必須（§4.1） |
| C-1 | 制約 | 抜粋には人名・案件名・顧客名が含まれ得る。出力は `out/`（`.gitignore` 済み）に限り、リポジトリにも Vault にも入れない | 機密の混入。運用上の最重要制約 |
| C-2 | 制約 | 記録ファイルには書き込まない。読み取りのみ | 利用者のセッション履歴を壊す |
| C-3 | 制約 | 実装は標準ライブラリのみ（`.ai/architecture.md`） | 依存追加には GR-023 |
| C-4 | 制約 | CI からは実際の記録を読めない。テストは同梱 fixture のみ | 実記録での動作は利用者がローカルで確認する（AC-5） |

## 3. 目的と範囲

- **目的（一文）:** 利用者が過去のセッションで行った日本語表現への指摘を、見落としなく候補として
  集め、仕分けとルール化に渡す。

- **成功指標（測定可能）:**

  | 指標 | 目標 | 測定方法 |
  | -- | -- | -- |
  | 再現率 | 仕分けで「指摘だった」と判定された発話のうち、候補一覧に含まれていた割合 90 % 以上 | 最初の仕分け時に、仕分け者が知っている指摘と照合（AC-6） |
  | 仕分けの負担 | 候補一覧のうちスコア上位 50 件で、確定した指摘の 8 割以上を含む | 仕分け結果の記録 |
  | 実行時間 | 500 MB の記録で 60 秒以内 | ローカル計測 |

- **範囲:** Claude Code のセッション記録の走査、候補の抽出とスコア付け、Markdown 一覧の出力、
  仕分け手順の文書化。

- **対象外（明示）:** 指摘の自動ルール化。Vault への書き込み。claude.ai（Chat）のエクスポート解析
  （優先度が低いだけで、対象から外す決定はしていない）。

## 4. 機能要件

| ID | 要件 | 目的との対応 | 優先度 | 根拠 |
| -- | -- | -- | -- | -- |
| FR-101 | `--projects-dir`（既定 `~/.claude/projects`）配下の `*.jsonl` を再帰的に読む。JSON として読めない行は数えて読み飛ばし、処理を止めない | 再現率 | Must | A-1。破損行で全体が止まると見落としになる |
| FR-102 | 人間の発話だけを対象にする: `type` が `user`、`message.role` が `user`、`isMeta` / `isSidechain` が真でない、`tool_result` ブロックを含まない | 仕分けの負担 | Must | ツール結果・自動生成メッセージは指摘ではない |
| FR-103 | 発話本文から `<system-reminder>…</system-reminder>` など `<タグ>…</タグ>` 形式の埋め込みブロックを除去し、残りが空なら対象外とする | 仕分けの負担 | Must | ハーネスが挿入する文面を指摘と誤認しない |
| FR-104 | 各発話に、同じセッション内で直前に現れた assistant の本文（`text` ブロックの連結）を対で付ける。無ければ空 | 再現率 | Must | A-2。何への指摘かが分からないと仕分けできない |
| FR-105 | 日本語（ひらがな・カタカナ・漢字）を含まない発話は対象外とする | 仕分けの負担 | Must | 対象は日本語表現への指摘 |
| FR-106 | スコア: `#表現` を含めば 10 点。強キーワード（わかりづらい / 分かりづらい / 不自然 / 言い回し / 表現 / AIっぽい / 揺れ）は種類ごとに 3 点。弱キーワード（ではなく / 直して / 言い換え）は発話が 200 文字以下のときだけ種類ごとに 1 点。スコア 0 の発話は候補にしない | 仕分けの負担 | Must | 2026-09-18 の実測: 弱キーワードの大半は作業指示 |
| FR-107 | 候補をスコア降順、同点は日時降順に並べる | 仕分けの負担 | Must | 上位から見れば負担が小さい |
| FR-108 | `--since YYYY-MM-DD` を受け取り、その日以降のレコードだけを対象にする | 運用 | Should | 元方針「直近 3〜6 か月」 |
| FR-109 | `--min-score N` で下限を指定できる（既定 1） | 仕分けの負担 | Should | 弱キーワードのみの候補を切れる |
| FR-110 | 出力は Markdown 1 ファイル。先頭に生成日時・対象ディレクトリ・期間・走査ファイル数・人間の発話数・候補数。候補ごとに、スコア・日付・プロジェクト（ディレクトリ名）・セッション ID・発話本文（400 文字まで）・直前 assistant 本文（200 文字まで）・一致したキーワード | 仕分け | Must | 仕分けに必要な情報を 1 か所に |
| FR-111 | 出力先は `--out`（既定 `out/candidates-<生成日>.md`）。`out/` が無ければ作る。既存ファイルは上書きせず終了コード 2 | C-1 | Must | 誤って別の場所に書かない。前回結果を消さない |
| FR-112 | 記録ディレクトリが無い、または `.jsonl` が 0 件なら理由を標準エラーに出し終了コード 2。正常終了は 0 | 運用 | Must | `rules` CLI と同じ終了コード体系 |
| FR-113 | 標準出力には要約 1 行（走査ファイル数・発話数・候補数・出力先）だけを出す | 運用 | Should | 抜粋を端末にも残さない（C-1） |

### 4.1 利用シナリオ（仕分けとルール化）

抽出の出力（候補一覧 `out/candidates-<YYYYMMDD>.md`）は、次の 3 段階を経て Vault の表現ルールになる。
役割の分担だけをここに定め、操作手順（コマンド・AI への指示文・各手順の期待結果と失敗時の対処）は
[docs/runbook/triage-correction-candidates.md](../runbook/triage-correction-candidates.md) が持つ。

| 段階 | 行う者 | 内容 |
| -- | -- | -- |
| 判定の提案 | AI | 候補一覧を読み、各候補が日本語表現への指摘か否かを判定理由付きで示す。指摘と判定したものは Vault の雛形 `rule-atom` を埋めた下書きをチャット応答として出す。ファイルは作らない |
| 採否の確定 | 利用者 | 下書きごとに採用・修正・不採用を決める。判定の最終責任は利用者にある（R-4） |
| 保存と検証 | 利用者（ファイル作成は AI に指示してよい） | 採用したルールを `30_memory/feedback/ja-<kind>-<slug>.md` に置き、`MEMORY.md` に索引を追記し、`make rules-validate` が 0 件で通ってから Vault を commit する |

仕分けの外で継続的に行うこととして、AI の日本語を直す発話に `#表現` を含める。FR-106 で
最高点が付くため、次回の候補一覧で上位に並ぶ（R-3 の対策）。

### 4.2 業務ルール

- 候補一覧は commit も共有もしない。仕分けが終わったら削除する。理由: 抜粋（発話本文と直前の
  assistant 本文）に人名・案件名・顧客名が含まれ得る（C-1）。
- 表現ルールの `## NG / OK` に候補一覧の抜粋をそのまま写さない。規則と、固有名を除いて一般化した
  例だけを書く。理由: 上と同じ。抜粋を写すと固有名が Vault に入り、昇格時の棚卸しが必要になる
  （Vault `AGENTS.md`「表現ルール」節の「書かないもの」）。
- 採否が確定する前に Vault へ書かない。下書きはチャット応答に留める。理由: 未確定のルールが
  次セッションから適用されるのを防ぐ。

### 4.3 状態と遷移

対象外（状態を持たない。実行ごとに全走査）。

### 4.4 役割と権限

対象外（ローカル実行。記録の読み取り権限は OS に従う）。

### 4.5 エラーと例外

| 状況 | 振る舞い |
| -- | -- |
| 記録ディレクトリが無い / `.jsonl` が 0 件 | 標準エラーに理由、終了コード 2（FR-112） |
| JSON として読めない行 | 読み飛ばして数え、要約に「読み飛ばし行数」を含める（FR-101） |
| `timestamp` が無い・解析できないレコード | `--since` の対象判定では除外せず含める。日付は「不明」と出力 |
| 出力先が既に存在する | 上書きせず終了コード 2（FR-111） |

## 6. データ要件

| 観点 | 仕様 |
| -- | -- |
| データモデル | 入力: セッション記録のレコード（JSON）。中間: 人間の発話（本文・日時・セッション・プロジェクト・直前 assistant 本文）。出力: 候補（発話 + スコア + 一致キーワード） |
| 想定量 | 数十〜数百ファイル、数 GB まで |
| 保持 | 保持しない。出力ファイルは利用者が管理・削除 |
| PII | 抜粋に人名・案件名を含み得る。`out/` 限定、commit 禁止（C-1） |

| ID | 基準 | 検証する要件 | 検証方法 |

| AC-1 | fixture の記録（人間の発話・ツール結果・meta・sidechain・system-reminder 混在）から、人間の発話だけが正しい本文で抽出される | FR-102, FR-103, FR-105 | 単体テスト |

| AC-3 | スコアの各規則（`#表現`・強・弱・200 文字条件・0 点除外）が仕様の数値で検証される | FR-106, FR-107, FR-109 | 単体テスト（期待値は本書の数値） |
| AC-4 | 一時ディレクトリの fixture に対して CLI が Markdown を書き、要約 1 行を出し、終了コード 0。既存ファイルがあれば 2。記録が無ければ 2 | FR-101, FR-110〜113 | 統合テスト |
